## 它解决什么问题

内联能拆掉函数边界：callee 里的常量、返回值、指针别名，在 caller 里第一次变得可见。但内联不是免费的——代码体积、编译时间、寄存器压力都会涨，冷路径上的大函数还会把 I-cache 撑坏。

所以内联器真正要回答的不是「能不能展开」，而是：**这条 call edge 值不值得消失？**

这个问题必须在正确的顺序里回答。内联会改写调用图本身，而 callee 的形态又会影响 caller 的代价。LLVM 因此把 `InlinerPass` 注册成 CGSCC pass：先处理 callee 所在的 SCC，再处理 caller；每次做决定时，callee 已经被优化过。这一页只讲「找哪些 call、怎么判定」；克隆、拆块和返回值合并属于 <a href={passUrl('/passes/inline-function/')}>inline-function</a>。

## 算法

先记住一句话：**SCC 后序决定「什么时候看」，候选队列决定「看哪些 call」，代价模型与 advisor 决定「收不收」。**

实验台的图固定为决策前的 call graph；8 帧只改变「当前检查哪个 SCC」与「这条 call 的判定」。拖动阈值会改变 `render → hash` 和 `main → render` 的结果；注意阈值调高时，callee 可能先吸收更多内联而变胖，caller 反而被拒绝。

### 后序：从叶子 SCC 往上

`LazyCallGraph` 把函数和 call edge 建成图，再把互相可达的函数缩成 SCC。SCC 之间不再有环，可以排序；`ModuleToPostOrderCGSCCPassAdaptor` 按后序访问，也就是先 callee、后 caller。

递归和互递归正是 SCC 存在的理由：`@hash` 与 `@mix` 互相调用，拓扑排序不存在，只能当成一个整体处理。CGSCC 遍历保证进入一个 SCC 时，它调用的所有子 SCC 都已经处理完——代价分析看到的是 callee 的最终形态，而不是半成品。

### 一个 SCC 内部的候选队列

`InlinerPass::run` 拿到一个 SCC 后，先把这个 SCC 里所有函数的 call site 收进一个 `SmallVector<CallBase*>`，按函数顺序、指令顺序排列。然后逐条处理；每次接受一条 call，`InlineFunction` 会把克隆进来的新 call site 交给 `IFI.InlinedCallSites`，它们被**追加到队列末尾**。

```text
calls = []
for F in SCC:
  for I in F:
    if isa<CallBase>(I) and has_definition(I.callee):
      calls.push(I)

for i = 0; i < calls.size(); ++i:        // size 会变
  if calls[i].caller 已经不在当前 SCC: continue
  if !eligible(calls[i]): continue
  ic = getInlineCost(calls[i])
  if ic.cost < ic.threshold:
    accept(calls[i])
    calls.append(new_calls_exposed_by_inline)  // 追加，不插队
```

追加而不是插队，是有意为之：先把当前 SCC 的这一轮扫完，再处理新暴露的传递调用。否则在一个高度互连的 SCC 里，每条边看起来都值得内联，函数会在互相内联中迅速膨胀。

### 属性闸门与 inline advisor

在算代价之前，有一批「不用算」的判定：

- `alwaysinline`、`flatten` 的 caller：直接 always；
- `noinline`、`optnone`、interposable、target feature 不兼容、含间接分支 / `blockaddress` / 可变参数：直接 never；
- 已经有 `!inline_history` 的 callee：直接 never，防止互递归无限展开。

这些闸门由 `getAttributeBasedInliningDecision` 和 `isInlineViable` 完成。之后 `InlineAdvisor` 才拿到候选：默认 advisor 调 `getInlineCost`，ML advisor 或 replay advisor 可以用自己的策略覆盖；`OnlyMandatory` 的第一次 pass 只处理强制项。advisor 还负责 deferral：如果把这个 callee 塞进 caller 会让 caller 自己错过上层内联，它可以建议先等一等。

### 代价模型：不是「小就内联」

`InlineCostCallAnalyzer` 从 callee 的 entry 做一次 BFS，只走对这个 call site 活跃的块：

- 常量实参会沿途折叠，分支条件已知就只走一边；
- 能化简的指令不计成本，化简不了的默认按 5 个单位算；
- 每个 call 另加 25 个单位的惩罚，调用点的参数准备成本会被减掉；
- callee 是单基本块时，阈值临时加 50%；向量密集时最多加 150%；
- internal 函数的最后一个 call site 直接减 15000——因为内联后整个函数可以删掉。

阈值默认 225（`-O2`），`-O3` 是 250，`-Os` 是 50，`-Oz` 是 5；带 `inlinehint` 时 325，热调用点可以到 3000，冷调用点降到 45。最终判定只有一行：

```cpp
return Cost < std::max(1, Threshold) ? success : failure("Cost over threshold");
```

分析可以提前退出：一旦成本越过阈值，就不再往下走。省下来的时间，正是内联器在大型模块里还能跑得动的原因。

### SCC 内部的额外设防

如果新暴露的 call 和刚被内联的 callee 仍在同一个子 SCC 里，call site 会带上 `function-inline-cost-multiplier`，每次乘以 `-intra-scc-cost-multiplier`（默认 2）。内联穿过子 SCC 的次数越多，下一次越贵。

互递归则靠 call site 上的 `!inline_history` 截断：同一个 callee 在历史里出现过，下一次 `CanInlineCallSite` 直接拒绝。成本乘子和 history 一个管「贵不贵」，一个管「会不会绕回来」，缺一不可。

### 决策之后

一条 call 被接受，`InlinerPass` 就把 `CallBase` 交给 `InlineFunction`；真正的参数替换、CFG 拆分、返回值 PHI、调试信息缝合都在那里发生。决策页到这里结束：它只产出「哪些 call 接受、哪些保留」的列表。

## 代价与坑

- **阈值是经验参数，不是语义。** 不同 LLVM 版本、target、profile 都会改数字。看 `-pass-remarks=inline` 的实际输出，比背 225 有用。
- **代码膨胀是真实的。** 内联把 callee 复制到每个 call site；热路径上的小函数值得，冷路径上的大函数会让 I-cache 和编译时间一起变差。
- **callee 先变胖，caller 再做决定。** 这是后序的代价，也是实验台里阈值调高反而拒绝 `main → render` 的原因。
- **递归不会无限展开。** 直接递归在 `isInlineViable` 就被拒绝；互递归靠 `!inline_history` 截断。
- **SCC 内部要额外设防。** `intra-scc-cost-multiplier` 和 `InlinedInternalEdges` 都是为「高度互连的 SCC」准备的，否则成本分析看起来每一步都划算，最后却会超线性增长。
- **profile 会改变结论。** 热调用点、冷 callee、cost-benefit 分析都可能绕过普通阈值；没有 profile 时，这些路径根本不会触发。

## 在管线里的位置

`-O2` / `-O3` 的默认管线把 `ModuleInlinerWrapperPass` 放在很前面：可选的 mandatory-first（只处理 `alwaysinline` 等强制项），再跑普通 `InlinerPass`。它被包在 `DevirtSCCRepeatedPass` 里，外面再套 `createModuleToPostOrderCGSCCPassAdaptor`，所以实际执行顺序是「按 SCC 后序 + 去虚拟化后重跑」。

内联之后紧跟着 SROA、instcombine、GVN 等函数级清理。这也是内联器愿意接受「现在看起来略亏」的 call 的原因之一：后续 pass 会把克隆进来的代码化简掉。

LLVM 还提供 `always-inline`、`module-inline`、`partial-inliner` 等变体；它们复用 `InlineCost`，但遍历和决策策略不同。决策通过后如何真正改写，见 <a href={passUrl('/passes/inline-function/')}>inline-function</a>。

## 自己跑一遍

```llvm
define internal i32 @scale(i32 %x) {
entry:
  %mul = mul i32 %x, 3
  ret i32 %mul
}

define i32 @total(i32 %x) {
entry:
  %sum = call i32 @scale(i32 %x)
  %res = add i32 %sum, 1
  ret i32 %res
}
```

```bash
opt -passes='print<inline-cost>' -disable-output demo.ll 2>&1
opt -passes='cgscc(inline)' -pass-remarks=inline -S demo.ll -o /dev/null
```

第一条逐条打印代价分析，适合对照本文的「5 个单位一条指令」看。第二条把决策打到 stderr，格式类似：

```text
inlined into ... with (cost=..., threshold=225)
```

具体数字随版本和 target 变化。若想同时看改写结果，去掉 `-o /dev/null` 并加上 `-S`；结果会输出到 stdout。

如果 `opt` 是 release build，`-debug-only=inline` 不可用，用 `-pass-remarks=inline` 就够了。

本机环境没有编译好的 `opt`，上面的 pass 名按 LLVM 当前 `PassRegistry.def` 校对，未实际执行；不同版本以 `opt -print-passes` 为准。
