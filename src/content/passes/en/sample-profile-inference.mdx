## What problem does it solve

A sampling profiler never tells you how many times an edge ran. It interrupts the program at a fixed period, records the PC, and attributes that PC to a function and a line or block through debug info or pseudo probes. The result is a set of **sparse, noisy block counts**:

```text
Samples cover only part of the function; the loop header has no probe:
  entry 100   loop ?   body 450   then ?   latch ?   exit 100

Treat missing as zero:
  entry 100   loop 0   body 450   then 0   latch 0   exit 100
  → loop and then look cold, and the back-edge flow has no explanation

profi infers:
  entry 100   loop 550 body 450   then 225 latch 450   exit 100
  → loop header = entry 100 + back edge 450, every block conserves flow
```

Filling gaps with zero cannot work. `entry` has 100 samples, all of which enter the loop; `body` has 450, so the back edge must carry 450 executions; `exit` has 100, so the loop can only leave 100 times. The `latch` has no samples: it receives body's 450 and sends it straight back. Together these force the loop header to 100 + 450 = 550. Set the missing `loop` to 0 and you get 100 ≠ 450 + 100; set `then` to 0 and body's 450 has nowhere to go. Everything that consumes block frequencies — BFI, the inliner, loop unrolling, block placement, Machine IR section assignment — then sees a profile that does not add up.

The old `sample-profile` loader used three rounds of `propagateThroughEdges`: copy the block count across a single predecessor/successor, or subtract the known edges from the block count when only one edge is missing. That rule is not guaranteed to converge on cycles, and when samples conflict it can only clamp an unknown edge to zero. The source carries a FIXME asking for a scheme that is guaranteed to finalise. More often the branch weights are badly distorted: in the loop experiment at the end of this page, without profi `opt` writes `function_entry_count = 1` and a `451 : 2` loop branch, while the branch inside the loop gets no `!prof` at all.

LLVM's profi replaces the local heuristic with a global objective. The comment at the top of the implementation says it directly:

> Given an incomplete and possibly imprecise block counts, the algorithm reconstructs realistic block and edge counts that satisfy flow conservation rules, while minimally modify input block counts.

In other words, **samples are soft constraints, not ground truth**. A block may gain or lose flow, but every unit of change has a price; among all integral solutions that conserve flow, the solver picks the one with the smallest total cost. Cycles, multiple paths and conflicting counts become one optimisation problem instead of being consumed by local rules.

It is worth being precise about what this is not:

- It is not a registered pass. The pass is `sample-profile` (`SampleProfileLoaderPass`); profi is the helper class `SampleProfileInference` / `applyFlowInference` inside the loader.
- It does not produce new samples and does not change the CFG. Its output is block and edge counts, later written as `function_entry_count` and `branch_weights`.
- It works on a **single function's** CFG. Cross-function context is the profile tree's job; see <I18nLink href="/passes/sample-profile-inline/">sample-profile-inline</I18nLink>.

## Algorithm

### Input: blocks, jumps and “unknown”

The loader first shapes the function CFG into a `FlowFunction`: one `FlowBlock` per block, one `FlowJump` per CFG edge. A block's weight comes from `getBlockWeight`, the maximum sampled weight of any instruction in it. A block with no sampled instruction is absent from `SampleBlockWeights`:

- `HasUnknownWeight = false`, `Weight = w`: sampled, and w may be 0;
- `HasUnknownWeight = true`, `Weight = 0`: not sampled, unknown.

Those two zeros are different. A known zero is an observation, and there is no capacity to decrease it; an unknown zero is the absence of an observation, so increasing it is free but there is nothing to remove.

Before building the network, the loader keeps only blocks that are **reachable from the entry and can reach an exit** (the intersection of a forward and a backward DFS). Blocks that cannot reach any exit — for example an infinite loop with no path out — never enter the network, and their samples do not affect the result. The entry is the block with no predecessors, an exit is a block with no successors; a function with one block or no positive samples returns early. If the entry block is known to be 0, the builder changes it to 1 so the network is not dead.

### The network: putting a price on “how much to change”

Every block is split into two nodes: `Bin = 2B` owns the incoming flow, `Bout = 2B + 1` owns the outgoing flow. A block's count is no longer a number but the total flow through the block. Splitting is what creates a place for the priced “increase” and “decrease” edges.

| Edge | Capacity | Cost | Purpose |
| --- | --- | --- | --- |
| `S → Bin` (entry) | ∞ | 0 | Connect the entry into the circulation |
| `Bout → T` (exit) | ∞ | 0 | Connect the exit into the circulation |
| `Bin → Bout` | ∞ | `inc(B)` | Increase this block's count |
| `Bout → Bin` | `w` | `dec(B)` | Decrease it, at most back to 0 |
| `S1 → Bout` | `w` | 0 | Inject the quota of sample w |
| `Bin → T1` | `w` | 0 | Drain the quota of sample w |
| `Bout(u) → Bin(v)` | ∞ | `inc(u,v)` | A CFG jump |
| `Bin(v) → Bout(u)` | `w` | `dec(u,v)` | Decrease an edge count (only if the edge carries samples) |
| `T → S` | ∞ | 0 | Close the circulation |

`S` and `T` are dummy nodes that connect the function entry and exit into one circulation; the actual source and sink of the optimisation are `S1` and `T1`. Every sampled block w receives w units of quota from `S1`, and those units must reach `T1` one way or another:

- **Keep** the sample: let the w units leave `Bout` along CFG edges, while other incoming flow enters `Bin` and drains to `T1`;
- **Reduce** it: send the quota through the reverse `Bout → Bin` edge and pay `dec`;
- **Increase** it: send extra flow through `Bin → Bout` and pay `inc`.

Max flow forces every quota into the network; min cost decides which blocks gain and which lose. The whole graph is a min-cost circulation: samples are flow that must be accounted for, and every edit is a detour with a price.

### Costs: the defaults decide the ties

The defaults in `ProfiParams` are not “stay as close to the samples as possible”; they are a hand-tuned price list. The current loader only assigns block costs in `applyFlowInference(FlowFunction&)`:

| Case | Increase | Decrease | Note |
| --- | --- | --- | --- |
| Normal sampled block | 10 | 20 | Increasing is cheaper than decreasing |
| Entry block | 40 | 10 | The entry has the most expensive increase; its count drives BFI for the whole function |
| Known zero block | 11 | 20 | Slightly worse than a normal block, so cold blocks are not lifted casually |
| Unknown block | 0 | 0 | Nothing to decrease, so the decrease capacity is 0 |
| Unlikely edge | 2³⁰ | 2³⁰ | Effectively forbidden |
| Other edges | 0 | 0 | The fields exist, but no command-line flag assigns them today |

The flags are hidden options:

```text
-sample-profile-profi-cost-block-inc=10
-sample-profile-profi-cost-block-dec=20
-sample-profile-profi-cost-block-entry-inc=40
-sample-profile-profi-cost-block-entry-dec=10
-sample-profile-profi-cost-block-zero-inc=11
-sample-profile-profi-cost-block-unknown-inc=0
```

“Unlikely” comes from `findUnlikelyJumps` and has exactly two sources: the unwind successor of an `invoke` (a landing pad), and a jump whose target block ends in `unreachable`. The former is an exceptional path, the latter should not execute by definition; charging `2³⁰` tells the solver to keep flow on the normal path.

The asymmetry changes results. Increasing an unknown block is free, decreasing a known block costs 20, and increasing a known block costs only 10 — so when samples conflict, profi prefers lifting a cold block or pushing a hot one down over trusting either side. When several solutions cost exactly the same, the even-flow rule below decides how to split.

### Solving: shortest augmenting paths, then an augmenting DAG

With the network built, `MinCostMaxFlow` repeatedly finds a shortest augmenting path from `S1` to `T1` in the residual graph:

- Reverse edges carry negative cost, but the network has no negative-cost cycles. The invariant `Dist(Source, V) ≥ 0` lets the search stop early: once the distance to `T1` is 0, or the current node's distance already exceeds `T1`'s, there is no need to expand it.
- Shortest paths are found with a queued Bellman-Ford (SPFA style), not Dijkstra, because negative-cost edges come from undoing previous augmentations.
- Every augmentation saturates at least one edge, and the flow increases monotonically until no positive-capacity path remains.

Shortest paths alone are not enough. `EvenFlowDistribution` (`-sample-profile-even-flow-distribution`, on by default in the CLI) handles the “several paths cost the same” case. It marks every edge that lies on a shortest path and has residual capacity at least `max(PathCapacity / 2, 1)`, collects those edges into an augmenting DAG with a bounded DFS (at most 10 visits per node), and then distributes flow by out-degree. Fractional remainders are rounded up and excess flow is sent back along reverse edges, so conservation holds and at least one edge saturates per DAG augmentation.

The animation is a concrete example. The `loop` header, `then` and `latch` have no samples, `body` has 450, and `entry` / `exit` have 100 each. The 450 back edge plus 100 entry pins the header at 550; 550 then splits into 450 for body and 100 for exit. The body's `then` / `latch` branch has no samples, so even-flow splits 450 into 225 / 225; on the simplified CFG in the animation, `rebalanceUnknownSubgraphs` produces the same even split, and only with both disabled does the unknown branch collapse (`body→then` 0, `body→latch` 450). If `then` carries 150 samples, the split becomes 150 / 300 (there is a verification command at the end of the page). **An even split is a tie-breaking rule, not a guess that the branch is 50 %.**

The source states a worst-case complexity of `O(v(f) · m · n)`, where `v(f)` is the max-flow value, `m` the number of edges and `n` the number of nodes; on typical instances it observes sub-quadratic running time. The DAG augmentation pushes a large batch of flow at once instead of one unit at a time, which is what makes it usable on real profiles.

### Extraction: block counts, edge counts and branch weights

After the flow converges, `extractWeights` translates network flow back into the CFG:

- Edge count = the edge's own sampled weight plus the auxiliary flow; self-loops additionally clamp the auxiliary flow to non-negative.
- Block count = `max(inflow, outflow)`. A block executes at least as often as any incident edge; taking the maximum avoids underestimating blocks with several predecessors and successors.
- The loader sets the function entry count to the inferred entry-block flow (`finalizeWeightPropagation`); only if that is 0 does it fall back to `head samples + 1`.
- Branch weights come straight from the flows on the terminator's outgoing edges. Unlike the old heuristic, profi's output is already integral and needs no `+1` correction to avoid zero-weight propagation. When several successors point at the same block, the loader splits that edge's weight across the duplicate edges, giving the remainder to the earlier successors.

### Post-processing: islands and unknown subgraphs

Min-cost flow guarantees conservation and minimum cost, not that the result looks like real execution. `FlowAdjuster` adds two clean-ups:

1. **`joinIsolatedComponents`**: if a block with positive flow is unreachable from the entry along positive-flow edges, it is an island. For each island, Dijkstra finds a shortest path from the entry to an exit that passes through it, and every edge and block on that path gains 1. `jumpDistance` prefers edges that already carry flow and penalises zero-flow and unlikely edges, so the repair follows the existing shape. It adds only 1; it does not move the whole island into the reachable region.
2. **`rebalanceUnknownSubgraphs`**: starting from a known, non-zero block, BFS through unknown blocks until it reaches known blocks. Only when the known sink is unique, the unknown subgraph is acyclic, and every unknown block still has a usable outgoing edge does it split each unknown block's outflow by out-degree (normally 50 / 50). This is a neutral prior for “what an unknown branch looks like”; min-cost flow on its own may put all of the flow on one unknown edge.

Both clean-ups are on by default (`-sample-profile-join-islands`, `-sample-profile-rebalance-unknown`). They do not change `Block.Weight` (the samples); they only adjust the inferred `Block.Flow`.

## Cost and pitfalls

- **It is not always on by default.** `-sample-profile-use-profi` starts as false; `doInitialization` enables it automatically only when the profile is context-sensitive, probe-based or preinlined. CSSPGO takes that path. A plain line-based AutoFDO profile needs the flag, otherwise the old three-pass propagation runs.
- **The cost model is not “recover the truth”.** The 10 / 20 / 40 numbers are tuned, not derived from a probability model. When samples conflict, the result can be a compromise that looks odd: entry 70, arms 50 and 100, join 100 comes out as entry 86, arms 19 and 67, join 86 (branch weights 19 : 67) rather than keeping 50 and 100. Minimum cost guarantees the cheapest total edit, not that every block stays close to its sample.
- **Ties are common.** Moving one unit of flow from A to B often means “A pays a little less, B pays a little more” for the same total. Augmentation order and even-flow decide the result; a different LLVM version or a changed default can change the numbers. Do not treat 225 : 225 or 50 : 50 as an invariant of the algorithm.
- **An even split for unknown branches is a prior, not evidence.** The 225 : 225 for then/latch in the animation is one such split. A function with only an entry sample will split evenly between two paths with completely different real hotness. Real CSSPGO puts pseudo probes on both paths, giving profi more anchors; a path without probes has only the prior.
- **Unlikely edges are pushed to zero.** An `invoke`'s unwind edge and a jump whose target ends in `unreachable` cost `2³⁰`; unless conservation forces them, their weight is 0. Exception paths and “looks unreachable” paths can therefore disappear from the profile, and EH-aware consumers see an over-hot normal path.
- **A loop with no samples does not invent iterations.** When only `entry` / `exit` are sampled and both `loop` and body are unknown, profi can set the back edge to 0: 100 calls split into 50 entering the loop and 50 exiting directly, with `loop` 50, body 0 and `exit` 100. Real CSSPGO needs probes inside the loop, otherwise the solver has no evidence to demand a single iteration.
- **Multiple successors sharing a destination lose information.** profi treats `(pred, succ)` as one edge. When several `switch` cases land on the same block, the loader can only split the edge weight again when writing `branch_weights`; the per-case difference is unrecoverable.
- **Unreachable blocks are dropped.** Blocks that cannot be reached from the entry, or cannot reach any exit, never enter the network. Samples on infinite loops with no way out take no part in inference and never appear in `BlockWeights`.
- **Unknown-subgraph rebalancing has preconditions.** The known sink must be unique and the unknown blocks must not form a cycle; otherwise `rebalanceUnknownSubgraphs` gives up, and a cyclic unknown region can keep an arbitrary split.
- **The entry count is overwritten.** The loader trusts profi's entry-block flow and writes it as `function_entry_count`, which may differ from the profile's head samples. A zero entry sample is also changed to 1. Consumers that treat “entry count = call count” need to know this.
- **Edge costs are currently zero.** The `CostJumpInc` / `CostJumpDec` / fall-through fields still exist, but `applyFlowInference` wires no command-line flags to them, so apart from unlikely edges, changing an edge count is free. Block counts are what the model actually optimises.
- **Sampling noise is not removed.** profi makes counts consistent, not accurate. When the profile is stale, the CFG changed, or probes were optimised away, stale-profile matching has to rescue the profile first; if it cannot, the most consistent solution can still be wrong.

## Where it sits in the pipeline

`sample-profile` (`SampleProfileLoaderPass`) is a module pass near the front of the simplification pipeline: after the profile is read, before the CGSCC inliner and most function passes. It processes functions one at a time, inlines hot call sites first, and then calls `computeAndPropagateWeights`; inside `propagateWeights`, it chooses profi or the old three-pass propagation. profi therefore sees the **post-inlining** CFG: inlining has already changed blocks and edges, and probe contexts have been materialised onto the new instructions.

For CSSPGO the order matters. The profile is context-sensitive; inlining expands a context such as `main:foo` into real blocks, and only after that expansion do the block counts make sense. For the same reason, profi's output is written straight into `!prof` for the later <I18nLink href="/passes/inliner/">inliner</I18nLink>, loop unrolling, block placement and <I18nLink href="/passes/machine-function-splitter/">machine-function-splitter</I18nLink>. <I18nLink href="/passes/hotcoldsplit/">hotcoldsplit</I18nLink> consumes the same BFI: its cold-block test uses the inferred frequency distribution, not the raw samples.

It is a different profile path from <I18nLink href="/passes/pgo-instr-gen/">pgo-instr-gen</I18nLink>: IR PGO inserts exact counters and reads them back in a second build, while profi's input is a sample profile that is incomplete by construction. Both end up as `!prof`, but one comes from counts and the other from inference.

In the default pipeline, `sample-profile` is a conditional module pass; profi is not a separate stage but a helper inside it. The atlas pipeline map draws it next to `sample-profile` and marks it as a helper.

## Run it yourself

The loop below is the same CFG as the animation, written in C so it can be compiled and run. The point is that **only some blocks have samples**: entry, the loop body and the exit have probes; the loop header and one branch inside the body do not.

```c
// loop.c
int sum(int n) {
  int s = 0;
  for (int i = 0; i < n; i++)
    if ((i & 1) == 0)
      s += 1;
  return s;
}
```

```text
# loop.prof
sum:100:0
 1: 100
 3: 450
 5: 100
```

Line numbers in a sample profile are **offsets from the function's start line**, not source line numbers. `sum` starts on line 1:

| Profile line | Source line | Block | Samples |
| --- | --- | --- | --- |
| `1` | line 2, `int s = 0;` | entry | 100 |
| `3` | line 4, `if (...)` | body | 450 |
| `5` | line 6, `return s;` | exit | 100 |

Line 3 (`for`) and line 5 (`s += 1`) deliberately have no samples, so the loop header, latch and then are unknown. `-fprofile-sample-use` also gives the function the `"use-sample-profile"` attribute; without that attribute the loader skips the whole function.

```bash
clang -O1 -g -fprofile-sample-use=loop.prof -Xclang -disable-llvm-passes \
      -S -emit-llvm loop.c -o loop.ll

opt -passes=sample-profile -sample-profile-file=loop.prof \
    -sample-profile-use-profi -S loop.ll -o loop.out.ll

grep -n 'branch_weights\|function_entry_count' loop.out.ll
```

With LLVM 23 the output looks like:

```text
!{!"function_entry_count", i64 100}
!{!"branch_weights", i32 450, i32 100}
!{!"branch_weights", i32 225, i32 225}
```

The first `branch_weights` is the loop condition: 450 executions go to body, 100 go to exit. The second is `(i & 1) == 0` inside the body: then and latch get 225 each. The loop header has no samples; its 550 = entry 100 + back edge 450 is constrained by both its inflow and its outflow.

Give the `then` arm 150 samples:

```text
sum:100:0
 1: 100
 3: 450
 4: 150
 5: 100
```

Run it again and the body branch becomes `150 : 300`: the sampled point anchors the split, while the loop header stays at 550 and the back edge stays at 450.

As a control, turn profi off:

```bash
opt -passes=sample-profile -sample-profile-file=loop.prof -S loop.ll -o loop.old.ll
grep -n 'branch_weights\|function_entry_count' loop.old.ll
```

The old heuristic writes:

```text
!{!"function_entry_count", i64 1}
!{!"branch_weights", i32 451, i32 2}
```

The loop exit is squeezed to 2 and the branch inside the loop has no `!prof` at all. It copied 450 along the back edge into the header but could not satisfy entry, back edge and exit at the same time; profi's 450 : 100 and 225 : 225 are solved together. That difference is why CSSPGO enables profi by default.

To watch the cost model change, override the prices; they are hidden options, but `opt` accepts them:

```bash
opt -passes=sample-profile -sample-profile-file=loop.prof \
    -sample-profile-use-profi \
    -sample-profile-profi-cost-block-dec=100 \
    -sample-profile-profi-cost-block-unknown-inc=1 \
    -S loop.ll -o loop.cost.ll
```

Setting `-sample-profile-even-flow-distribution=false` changes the body branch from 225 : 225 to `0 : 450`, so on this C loop the even split comes from even-flow; `rebalanceUnknownSubgraphs` does not step in for this CFG. Adding `-sample-profile-rebalance-unknown=false` does not change that result, but it does affect unknown subgraphs that satisfy the unique-known-sink and acyclic conditions. To see the augmentations themselves you need an assertions build and `-debug-only=sample-profile-inference`; release binaries usually do not expose that flag.
